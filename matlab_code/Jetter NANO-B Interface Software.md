# **System Architecture and Protocol Specification for Bridging Jetter NANO-B PLCs to Modern Computing Environments**

## **Introduction and Historical Context**

The integration of legacy industrial control systems into modern computing architectures presents distinct challenges spanning physical interface compatibility, data link framing, memory addressing, and execution concurrency. The Jetter NANO-B Programmable Logic Controller (PLC) is a compact, process-oriented automation controller historically deployed in sophisticated handling systems, single-axis to multi-axis robotics, and complex automation environments1. Because these units were designed during the late 1990s and early 2000s, their primary software interfaces rely on antiquated operating systems, specifically Windows 98 and Windows ME, utilizing 32-bit Dynamic Link Libraries and proprietary serial protocols4.

Modern software engineers seeking to produce a reliable communication bridge between contemporary operating systems and the Jetter NANO-B must deconstruct the historical software stack that originally facilitated this connection. In its native era, the NANO-B was programmed using a plain text high-level language called SYMPAS, which was later succeeded by the JetSym programming environment2. Unlike conventional cyclic PLCs, Jetter PLCs utilize a multitasking, process-oriented storage run where tasks are permanently checked for input conditions required to continue the control flow, rather than executing a top-down cyclical scan2. This architectural philosophy implies that the data traffic bridging the PC and the PLC must be highly deterministic, as injecting data asynchronously into a multitasking environment requires careful handling of shared memory registers. This report provides an exhaustive technical analysis of the software interface, protocol specifications, data traffic framing, and architectural requirements necessary to construct a robust data bridge, entirely bypassing the need for legacy Windows 98 hardware.

## **Legacy Software Architecture and Driver Dependencies**

The original software bridge designed for Windows 98 environments relied heavily on a centralized library to abstract the complexities of the serial protocol. To understand the data traffic properly, it is necessary to examine the specific files and drivers that historically ran the system.

### **The Jet32.dll Application Programming Interface**

In historical deployments, communication with the NANO-B was encapsulated within Jet32.dll, a 32-bit Windows Dynamic Link Library4. This library exposed a C-style Application Programming Interface (API) to user-space applications, serving as the sole conduit for serial data exchange. Any user-facing software, such as human-machine interfaces (HMIs) or analytical tools, passed high-level commands to this DLL, which in turn generated the raw serial bytes.

An analysis of surviving source code from academic environments, specifically a MATLAB MEX wrapper written in C (nanomex.c) and its corresponding MATLAB interface script (nanocom.m), reveals the exact execution flow and function exports of the Jet32.dll driver4. The C code demonstrates that establishing a bridge requires initializing a connection handle and subsequently invoking specific memory access functions.

The primary initialization function, Jet32Connect, requires the target COM port, a device type constant (JET32\_CT\_NANOB), and returns a handle to the interface4. If the connection fails, the software must invoke Jet32GetLastError() to extract the specific diagnostic code generated by the library4. Once the connection handle is established, the legacy software utilizes a specific set of character flags to dictate the type of data traffic being requested. By mapping these flags to their corresponding Jet32.dll API calls, modern developers can understand the exact operations supported by the controller.

| Command Flag | Operation Description | Underlying Jet32.dll Function |
| :---- | :---- | :---- |
| g | Get Register (Read 24-bit value) | Jet32GetRegister |
| s | Set Register (Write 24-bit value) | Jet32SetRegister |
| h | Get Flag (Read internal boolean) | Jet32GetBool with JET32\_BT\_FLAG |

### **The Read-Modify-Write Concurrency Vulnerability**

A critical operational constraint of the legacy Jet32.dll driver is exposed by the w command flag in Table 1\. The historical documentation explicitly notes that the capability to write to a single bit within a specific register is fundamentally absent from the Jet32.dll implementation4.

To circumvent this limitation, legacy software bridges implemented a software-level Read-Modify-Write (RMW) cycle9. When a user application requested a single bit change, the MATLAB script nanocom.m would first read the entire 24-bit register from the PLC into the PC's local memory. The PC would then modify the target bit locally using a bitwise setter function, and subsequently write the entire 24-bit integer back to the PLC via the SetReg command9.

This mechanism introduces a severe concurrency flaw known as an RMW race condition10. The Jetter NANO-B operates on a multitasking OS capable of executing parallel SYMPAS tasks. If the PLC's internal logic modifies an adjacent bit within that exact same register during the millisecond window that the PC is executing its local modification, the PC's subsequent write command will blindly overwrite the PLC's internal memory, destroying the state change executed by the PLC2. When constructing a modern software bridge, developers must completely avoid implementing RMW cycles from the PC side for critical state registers. Instead, bitwise modifications must be handled by dedicating individual boolean flags within the NANO-B memory space, pushing a flag state from the PC, and allowing the PLC's internal process logic to safely commit the bitwise mutation within its own protected clock cycle.

## **Physical Interface and Serial Synchronization**

The foundation of the bridge between a modern PC and the Jetter NANO-B unit lies in the physical serial interface. The NANO-B utilizes standard RS-232 and RS-422/485 electrical topologies, but the physical pinouts and default port configurations deviate from standard personal computer serial implementations11.

The default serial communication parameters for the Jetter NANO-B programming and communication interfaces operate at a standard baseline to ensure compatibility with older terminal equipment. The primary configuration dictates a baud rate of 9600 bits per second, utilizing 8 data bits, no parity, and 1 stop bit, universally designated as an 8N1 configuration12. While this default baud rate can be dynamically elevated up to 115,200 bps for the serial port, or up to 1 MBaud for the internal CAN-based system bus, any modern software bridge must hardcode its initial handshake sequence to 9600 8N112. Attempting to connect at higher baud rates without prior negotiation will result in framing errors and dropped packets.

A critical hardware-software boundary issue in Jetter communication is the physical DB9 connector pinout. Standard RS-232 implementations typically utilize Pin 2 for Receive Data (RxD), Pin 3 for Transmit Data (TxD), and Pin 5 for Signal Ground (GND). However, the Jetter NANO-B CPU port features a proprietary layout that necessitates customized null-modem cabling. Historical wiring diagrams indicate that the controller's DB9 male connector assigns the pins differently from a standard terminal device17.

| Signal Description | PC / HMI Side (Standard DB9) | Jetter NANO-B Side (DB9) |
| :---- | :---- | :---- |
| **Transmit Data (TxD)** | Pin 3 | Pin 2 |
| **Receive Data (RxD)** | Pin 2 | Pin 3 |
| **Signal Ground (GND)** | Pin 5 | Pin 7 |

Table 2: Serial Pinout mapping illustrating the required crossover between a standard PC DB9 interface and the Jetter NANO-B7.

The most prominent divergence is the use of Pin 7 for Signal Ground on the Jetter PLC side, as opposed to the industry-standard Pin 57. Any modern PC bridge utilizing a contemporary USB-to-RS232 adapter must utilize a custom-soldered cable crossing Pin 2 and Pin 3, while explicitly routing the PC's Pin 5 to the Jetter's Pin 7\. Failure to establish a common electrical ground via Pin 7 will result in floating voltages. At the software layer, this electrical mismatch manifests as continuous parity failures, garbled payloads, and driver timeouts, rendering the software bridge completely inoperable.

## **Data Link Layer: The PCOM7 Protocol and Framing Architecture**

Once physical synchronization is achieved, the software bridge must parse the data traffic. The NANO-B natively utilizes Jetter's proprietary serial protocol, known as PCOM7 (historically referred to as the PC-PPLC protocol)6. Standard industrial drivers, such as generic ASCII or Modbus RTU implementations, cannot natively interpret PCOM7 out of the box because of its highly specific encapsulation mechanisms12. Understanding the byte framing and checksum calculations is paramount for translating the data traffic.

### **Non-Standard Control Characters**

Most ASCII-based industrial protocols utilize the standard ASCII control characters 0x02 for Start of Text (STX) and 0x03 for End of Text (ETX). The Jetter NANO-B serial interface fundamentally breaks from this convention. The engineering rationale behind this deviation is rooted in payload collision prevention; because the protocol transmits raw binary values representing 24-bit integers, standard control characters like 0x02 frequently occur naturally within the numerical data payload.

To ensure that intermediate modems or terminal buffers do not accidentally interpret a payload byte as a control command, the Jetter protocol defines its framing bytes in the extended ASCII range:

* **STX (Start of Text):** The hexadecimal value 0xDA (Decimal 218\)12.  
* **ETX (End of Text):** The hexadecimal value 0xDB (Decimal 219\)12.

A modern software bridge must utilize raw port access to interact with this data stream12. High-level abstractions that attempt to auto-parse strings based on carriage returns or standard STX/ETX characters will fail. The software buffer must continuously scan the UART FIFO queue specifically for the 0xDA byte. Once identified, all subsequent bytes are pushed into an internal payload buffer until the 0xDB byte is encountered. This frame encapsulation is non-negotiable; standard terminal emulators will render these bytes as extended ASCII garbage characters, a phenomenon which has historically caused significant confusion when engineers attempt to reverse-engineer the raw data traffic via serial monitors.

### **Packet Structure and Data Integrity Verification**

Once the 0xDA and 0xDB framing bytes are stripped by the driver's receiving loop, the internal payload constitutes the PCOM7 command frame. The structure of this packet generally adheres to a deterministic layout designed for rapid parsing by the PLC's microcontroller6. The packet begins with a Node ID, which identifies the target PLC on a multidrop serial or JETWay network, followed immediately by a Command Code instructing the PLC to perform a specific action6. This is followed by the Address Field designating the target memory register, and the Payload Data containing the values being written or returned.

Integrity verification in Jetter's serial traffic depends on the specific protocol configuration, but raw PCOM7 communications frequently utilize a Block Check Character (BCC) mechanism rather than a heavier 16-bit Cyclical Redundancy Check (CRC)6. The BCC is calculated using an iterative logical XOR operation across all bytes in the payload, explicitly excluding the STX and ETX characters.

A modern bridge software must programmatically implement this XOR routine to validate incoming traffic and to sign outgoing requests. The algorithm requires initializing a byte variable to zero, iterating through the payload buffer to apply the XOR operation against each byte, and appending the resulting checksum byte immediately prior to the 0xDB ETX byte. If the NANO-B receives a frame where the calculated BCC does not match the transmitted BCC, it will silently discard the packet or return an error flag in a subsequent response frame6.

## **Register Architecture and Memory Addressing Anomalies**

Understanding the Jetter NANO-B’s memory map is the most critical requirement for developing a functional software bridge. The serialized data traffic moving across the PCOM7 link ultimately resolves into read and write operations executed against the PLC’s internal register and flag architecture13. The design of this architecture features several distinct anomalies that will cause modern high-level programming languages to throw out-of-bounds errors or corrupt data if not properly handled.

### **The 24-bit Integer Processor Architecture**

The most distinctive characteristic of the Jetter NANO-A/B/C/D controller family is its internal 24-bit integer processor architecture23. While modern computing systems universally operate on 32-bit or 64-bit boundaries, the NANO-B stores and processes all standard integers within a rigid 24-bit space7.

The mathematical limits of this 24-bit space dictate that the valid range for any signed integer is exactly \-8,388,608 to \+8,388,607 in decimal notation, corresponding to 0x000000 to 0xFFFFFF in hexadecimal7. This architectural reality introduces significant computational complexities for bridge software running on a modern personal computer. When a modern driver—written in C\#, Python, or C++ and utilizing standard 32-bit Int32 or DWORD types—attempts to write a negative number to the Jetter controller, the PC will format the number using 32-bit Two's Complement representation. This process inevitably populates the most significant bits (Bits 24 through 31\) with ones.

If the bridge software transmits a full 32-bit frame where bits 24 through 31 contain non-zero data, the Jetter operating system will immediately reject the packet. The NANO-B firmware strictly enforces a rule that the highest 8 bits of a communication word must be absolutely zeroed. Violating this rule halts the operation and triggers a "Value is Incorrect" fault on the controller's diagnostic interface19.

To circumvent this, any custom software bridge must implement a middleware serialization layer that explicitly sanitizes the data before transmission. For positive values, the software must apply a bitwise AND mask (value & 0x00FFFFFF) to guarantee the top 8 bits are stripped19. For negative numbers, the software must manually recalculate the 24-bit Two's Complement representation, ensuring the 24th bit serves as the sign bit, before encapsulating the data into the serial payload.

### **Double Word Overlapping and Memory Alignment**

When the NANO-B requires data larger than 24 bits, such as IEEE floating-point numbers or 32-bit extended counters, it utilizes an overlapping "Double Word" scheme that spans two sequential registers19. The alignment of these words depends heavily on the specific addressing command utilized in the PCOM7 protocol.

In a standard setup, if a read/write address format addresses multiple words utilizing the WRn command format, the low word consisting of Bits 0-15 resides in register n, while the high word resides in register n+1. However, if the address format utilizes the native 24-bit register command (Rn), then the lower 24 bits reside in Rn and the upper bits reside in Rn+119. A modern software bridge must maintain strict state tracking of the data type being requested from the PLC. If the bridge attempts to fetch a floating-point number without accounting for this dual-register spread, the resulting data will be severely corrupted due to the misalignment of the mantissa and exponent across the 24-bit register boundaries.

### **Index Endianness and Bit Shifting**

Another critical nuance highlighted by the legacy Windows 98 drivers involves bit index alignment. The legacy MATLAB nanocom.m code contains explicit commentary regarding bitwise array handling, stating that the Least Significant Bit (LSB) in modern environments like MATLAB or C is defined as zero, whereas within the NANO-B architecture, the LSB is defined as one9.

The Jetter NANO-B counts its bits starting at index 1 up to 24\. A software bridge converting modern bit-masks to Jetter requests must mathematically shift the bit indexing by \-1 prior to interpreting the payload. Failure to implement this offset will result in all Input/Output toggles and flag modifications being off-by-one, triggering the wrong physical relays on the factory floor.

## **System and Special Configuration Registers**

The NANO-B exposes a highly specific segment of its memory map—predominantly the 2000-series registers—for hardware configuration, low-level diagnostics, and system bus management8. A modern software bridge can dynamically query these registers to adapt to the PLC's state, rather than relying on hardcoded assumptions. The contents of these user registers are maintained in battery-protected RAM, meaning their state persists across power cycles13.

## **Network Routing and Distributed Topologies via JETWay**

Industrial automation systems rarely consist of a single, isolated standalone PLC. The Jetter NANO-B is frequently deployed as a centralized master node within a larger hierarchical network using the proprietary JETWay system bus13. Understanding the JETWay architecture is vital if the modern PC bridge is physically connected to one Master NANO-B, but requires the extraction of data from secondary Slave NANO-B units cascaded downstream on the factory floor.

### **JETWay-H and JETWay-R Hierarchies**

The JETWay network is logically divided into two distinct communication tiers, each serving a specific operational purpose:

* **JETWay-H (Data Highway):** This upper tier is designed for high-level visualization, programming via the JetSym or SYMPAS environments, and direct PC-to-PLC data transfer13.  
* **JETWay-R (Process Level):** This lower tier is designed strictly for real-time, peer-to-peer data exchange between PLCs8. The NANO-A model, for instance, can only function as a slave on this specific network tier8.

### **Arithmetic Routing via the 50,000 Register Offset**

When bridging data, reading a local register on the directly connected Master controller simply requires a standard PCOM7 addressing command. However, reading a register located on a downstream slave device connected via JETWay-R requires an arithmetic offset mechanism embedded deeply within the Jetter protocol13.

The Jetter operating system routes network requests utilizing a base offset of 50,000. To access a specific register on a slave controller, the bridge software must calculate the target address using the slave's physical network node ID16. Rather than encapsulating a new IP-like packet with a specific destination MAC address, the bridge software requests a specific virtual register mathematically mapped into the Master PLC's memory space.

For example, if the software bridge needs to read Register 200 on slave node number 3, it applies the offset calculation. The Master PLC receives this request, recognizes that the memory address falls within the 50,000-range, and transparently proxies the request across the JETWay-R bus to the slave unit16. The slave responds to the Master, which in turn hands the 24-bit value back to the PC bridge over the serial line. This allows the modern PC software to remain entirely agnostic to the physical topology of the downstream industrial network, interacting with a vast multi-node system as if it were a single contiguous memory block.

Furthermore, internal program logic running on the NANO-B utilizes explicit N-SEND and N-GET commands within the SYMPAS language to push and pull data between these distributed nodes asynchronously7. A sophisticated bridge driver on the PC side can dynamically monitor the specific N-GET buffer registers on the Master PLC to passively intercept telemetry data as it arrives from the slaves, thereby preserving precious serial bandwidth by eliminating the need to continuously poll the downstream devices.

## **Architectural Strategies for Modern Bridge Implementation**

Armed with the physical layer constraints, the PCOM7 protocol specifications, and the intricacies of the 24-bit memory architecture, an engineering team possesses multiple strategic pathways to connect a modern 64-bit personal computer to the legacy NANO-B unit. Each approach balances initial development time against long-term deployment stability and cross-platform flexibility.

### **Strategy A: Hardware Protocol Converters**

The most resilient, though potentially most capital-intensive, method is to eliminate the need for custom serial parsing software entirely by inserting an industrial protocol converter between the modern PC and the PLC. Network gateways from manufacturers such as Red Lion, HMS Anybus, or Exor offer built-in, pre-compiled drivers specifically for Jetter’s PCOM7 protocol6.

In this architecture, a gateway device is physically wired to the NANO-B via the custom RS-232 DB9 cable, utilizing the crossed Tx/Rx and Pin 7 ground configuration12. The gateway is configured via its respective proprietary IDE to utilize the "Jetter Raw Port" driver6. The gateway's internal firmware autonomously handles the injection of the 0xDA and 0xDB framing bytes, and automatically calculates the XOR BCC checksum on the fly12. The gateway translates the 24-bit Jetter registers into standard 16-bit Modbus Holding Registers or OPC UA nodes. The modern PC subsequently connects to the gateway via standard Ethernet, entirely isolating the modern IT infrastructure from the legacy timing constraints and electrical noise of the serial bus25.

### **Strategy B: 32-bit IPC Wrapping of Jet32.dll**

If procuring hardware gateways is not feasible, the legacy Jet32.dll can theoretically still be utilized. However, a legacy 32-bit DLL cannot be directly loaded into a modern 64-bit application, as modern Windows operating systems strictly prohibit the mixing of 32-bit and 64-bit memory spaces within a single process.

To bypass this, developers must create a small, dedicated 32-bit executable compiled explicitly for x86 architectures. This microservice acts as a wrapper, loading the Jet32.dll library into memory and invoking the core functions (Jet32Connect, Jet32GetRegister) identically to the historical MATLAB C-code4. This 32-bit microservice acts as an Inter-Process Communication (IPC) server, hosting a lightweight REST API or WebSocket server on the local machine. The primary 64-bit modern application communicates strictly over standard TCP/IP to the 32-bit microservice, which in turn acts as the execution engine for the legacy DLL. This avoids the need to reverse-engineer the PCOM7 serial frames entirely, though it irrevocably ties the solution to Windows OS environments and inherits the Read-Modify-Write concurrency vulnerabilities inherent to the original driver4.

### **Strategy C: Native Protocol Reimplementation**

For maximum system flexibility, cross-platform compatibility, and complete independence from legacy Windows libraries, the bridge can be written entirely from scratch by communicating directly with the raw serial port using modern languages such as Python or C\#.

Using standard libraries, the software binds to the COM port at 9600 baud, 8N113. The software implements a byte-level parser that continuously monitors the buffer. The transmission function manually encapsulates outbound requests with the 0xDA Start of Text character, calculates the XOR BCC block check, and closes the frame with the 0xDB End of Text character12. The receiving function blocks execution until 0xDA is detected, buffers the payload, verifies the checksum, and extracts the data.

Critically, this native approach requires the software to manually enforce the 24-bit integer limits, applying the & 0x00FFFFFF bitmask prior to transmission to prevent the controller from faulting on negative numbers19. Furthermore, the software must account for the base-1 bit indexing anomaly when mapping bitwise operations to ensure the correct physical relays are actuated9. While this strategy requires rigorous unit testing to ensure the serial buffer timing is resilient against physical line noise, it provides total programmatic control and allows the Jetter NANO-B to be directly integrated into modern cloud-native IoT platforms without intermediary hardware or legacy operating system constraints.
